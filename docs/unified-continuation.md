# 人工继续原任务

点击“继续任务／继续复查”、在聊天中单独发送“继续／继续任务／继续复查”，或对独立 CLI 任务执行
`python -m agent.cli.tasks --state-dir <原目录> --continue`，都继续原记录。不会另开任务，也不会清零累计消耗。
纯继续指令由程序识别，不先请求 Chatbot；疑问、否定、引用中的“继续”及附带新要求的消息不按纯命令处理。
附带新要求时，先保存原文、确认新的交付方案，再将确认的版本与继续指令交给原内核。

| 停止类别 | 明确继续后的处理 |
|---|---|
| 暂停、取消 | 核对原件和环境，解除这次停止标记，继续原游标 |
| 安全边界导致的运行异常 | 保留错误与配对记录，核验未知结果、原件、权限和环境后继续；不盲目重发 |
| 调用、Token、任务时间或服务额度耗尽 | 只给耗尽维度追加一批原始额度；零服务预算仍不授权付费服务 |
| 已验收成功 | 保存此前成功结果，开启新的复查轮；不得把缓存成功算成本次复查 |
| 已有命令结束或结果不明 | 重新保存只读现场检查；不自动再次执行原副作用命令，进一步执行需确认新方案 |
| 原件损坏、内核缺失、权限不足、环境缺失 | 显示具体条件，保持停止；继续按钮不等于绕过校验或批准权限 |

工作内核中的模型受阻、普通参数拒收、重复计划、纯文字回复和验收失败直接返工，不产生等待人工继续的停止。验收次数累计保留，普通验收失败自动返工；默认不设工作模型调用次数上限，仍遵守 Token、时间以及用户明确设置的调用／费用上限。完整空回复可继续纠正，响应未知、截断及存储故障不会按普通错误重发。

旧任务仍使用绑定的旧内核。宿主仅保留旧停止记录的读取与命令投递协议，不把旧轮数停机实现留在新内核。

## 恢复协议 2

后端统一给出 `continuation`：`protocol`、`available`、`stop_id`、`mode`、`requirements` 和 `additions`。
网页不再维护一份停止状态白名单。提交命令携带原 `resume_token`；后端事务绑定原任务和当前停止身份。
重复点击、重复投递合并，派发前再次核对身份；已运行的任务只确认当前状态。过期页面必须刷新后再决定。
独立 CLI 的继续编号由原任务与停止身份确定，同一断点不会得到两笔追加授权。

原生 `continuation_history` 保存继续命令、此前原因、取消标记、验收结果和累计值。
`budget_grants` 记录追加前后限额与命令；恢复时重新核对追加账本，不能通过传入新预算替换旧消耗。
`stops/<stop_id>.json` 保留首次停止结果，`result.json` 仅为最近一次投影。
原命令、原响应、已完成步骤、验收与连续检查点日志仍是原件，不建立第二套执行检查点。

应用库从版本 1 事务迁移到 2，增加命令的停止身份字段，迁移前备份。工作管道版本 2 使用存活心跳。
旧协议 1 保留读取与停止能力；缺少失联保护的旧内核不能在新版中悄悄恢复执行，需要单独明确迁移。
从协议 2 基准开始，未来应用继续调用任务绑定的不可变内核，不自动替换提示、算法或验收。

普通停止、成功与退出只停止执行者，保留任务引用的容器、镜像、依赖和内核。
永久删除仍使用已有归属与引用校验，不扩展到共享缓存、其它应用或历史评测资源。

旧协议任务没有通用自动迁移入口，须针对原记录单独核验并明确批准。产品更新、离线验证或环境准备不构成启动新的付费评测的授权。
