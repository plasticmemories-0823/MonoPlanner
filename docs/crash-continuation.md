# 崩溃后的手动断点续跑

应用或内核崩溃后不自动继续派发。当前受管容器由[失联看守](lifetime-safety.md)在撤销或超时后停止；重新打开应用核对已有记录、收拢遗留所属执行，不调用模型、不推进任务工具。
用户点击“继续任务”后，仍使用原任务、原内核和原环境，核对断点再推进。
普通聊天、刷新和补充不能替代这次继续指令；在聊天中单独发送“继续”等纯命令，按[统一继续入口](unified-continuation.md)处理。手动暂停保持暂停直到明确继续。
崩溃前已经确认的需求补充按原 ID 和顺序保留，点击继续后交给原内核去重处理。
尚未完成需求确认的补充保留原文，先确认更新后的方案，不能悄悄忽略它继续旧目标。

## 记录顺序

1. 派发前保存请求、操作身份和预算预留。
2. 完整响应或执行结果先写临时文件，刷盘后原子发布。半写文件不能当作回执。
3. 检查点携带上一份检查点哈希、完整状态及本次原件引用，再原子发布。
4. SQLite 索引和界面事件随后登记；它们不再是判断工具是否已完成的唯一来源。

任务租约确保只有一个执行者能补登记或推进游标。索引漏登记时按连续日志链补齐；
任务索引丢失或损坏时保留损坏文件，再从完整原件重建。日志缺页、分叉、原件变化仍拒绝恢复，
不能从多个不一致版本中猜一个。

## 继续时如何处理

| 断点 | 行为 |
|---|---|
| 模型完整响应已保存，检查点未更新 | 核对请求与响应身份，补计已知用量，消费原响应，不重新请求 |
| 请求已发送但完整响应丢失 | 只结算一次未知预留；点击继续后才允许下一次请求，未知费用不算零、不释放 |
| 代码命令完成，SQLite 尚未登记 | 从步骤原件或绑定该命令的进程回执补登记，推进原游标，不重复命令 |
| 受管代码命令只执行了一部分 | 保留原件与当前改动，结束旧计划中的未决步骤；先只读调查，再制定修复，不直接重放原命令 |
| 验收已经完成，检查点未更新 | 核对候选、冻结验收和结果哈希，复用原结果，不再运行验收 |
| 隔离验收中途停止 | 保留未完成尝试；显式继续后在新的隔离目录执行原验收，不覆盖旧结果 |
| 摘要已返回，视图提交中断 | 核对原历史及摘要，幂等完成本地提交，不再次请求摘要 |
| 任务已经完成，界面没收到最后状态 | 从原内核的已提交终态恢复显示，不重新创建已回收的容器 |
| 聊天工具回执已保存，工具消息缺失 | 补齐原调用对应的工具消息，不派发工具 |
| 聊天工具缺少回执 | 明确配对为未派发或结果未知，不伪称“未执行”；原操作不自动重试 |

Docker 命令的输出和最终状态由容器内执行器直接保存，避免仅依靠宿主 Docker CLI 的返回值。
恢复必须核验原容器的完整身份、镜像、挂载和隔离；仍运行的原容器要先确认停止，不能另建容器冒充原现场。

## 不变的保护

- 原始需求、冻结验收、权限和用户固定命令不变。
- 累计调用、Token、未知预留、验收次数和已记录耗时不清零。缺失的耗时不能冒充精确零耗时。
- 用户继续命令有唯一身份；重复递交不能多追加一次已耗尽预算或派发第二个执行者。
- 内核、环境或不可变原件缺失时给出明确诊断。不会通过忽略身份校验来恢复。
- 外部应用、远端服务或任意非事务命令没有回执且不能查询时，无法证明其副作用是否发生。
  这类操作不会被透明重放，也不能宣称能够从任意机器指令恢复；需要其自身的幂等或检查点协议。

这些规则是 1.0.0 正式初版的恢复基准。后续升级保留任务绑定的内核，不能修改历史冻结源码来套用新恢复逻辑。
升级方式见[升级与旧任务续跑](upgrade-compatibility.md)。
