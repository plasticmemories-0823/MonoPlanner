# 验收轮次与断点续跑

## 使用

1. 达到本批验收轮次上限而仍未通过时，工作保存断点，状态为 `acceptance_limit_reached`。聊天中会显示累计次数、最近验收结果和下一批额度。提示直接来自已提交记录，不依赖进度模型是否可用。
2. 查看已有改动及诊断后，点击“继续任务”。默认追加 3 轮；使用内核自定义 `max_rounds` 创建的任务沿用创建时的批量大小。
3. 仍使用同一任务 ID、工作区、冻结验收和执行游标。已完成的操作或已保存的验收不会重新执行。又用完一批时再次暂停，等待新的决定。
4. 不想继续时可保持暂停。刷新、重启、普通状态询问、补充消息及重复点击不会追加额度。任务必要记录及绑定环境在等待期间保留。

独立任务 CLI 明确续跑：

```sh
python -m agent.cli.tasks --state-dir /absolute/path/to/records --continue-acceptance
```

`--status` 和 `--find` 只读查询；单纯重新运行 CLI 不会批准增加验收额度。其它暂停类型原有行为不变。

## 预算与记录

- `acceptance_budget.round_limit` 是累计允许验收次数，`round_increment` 是单次人工批准增加的次数。
- `rounds` 始终保存完整累计验收历史，不清零；每次批准写入 `acceptance_limit_history`，记录暂停 ID、控制命令 ID 和新的累计上限。
- 模型调用、Token、服务费用、总耗时等预算独立累计。本功能只增加验收轮次，不解除其它预算或安全限制。继续可能发生新的模型费用。
- 最后允许的一轮通过时直接成功；失败时立即暂停，不再为了发现上限额外生成下一份候选。
- 若检查点已有候选及部分已完成步骤，防御性的上限检查保留原计划、已完成行和游标；批准后只接续剩余部分。

## API 与并发

原有 `resume` 控制命令仍适用。验收额度暂停时，客户端必须传入匹配的 `acceptance_pause_id`，值来自当前快照中的 `work.acceptance_limit.pause_id`。省略字段或携带旧暂停 ID 的请求会被拒绝，避免延迟到达的普通恢复命令批准未展示的新额度；UI 与 CLI 均显式携带该字段。其它暂停类型仍保留原有恢复行为。

应用把同一暂停上的重复点击合并，执行内核在独占任务租约内原子提交一次额度增加。直接调用 `TaskRunner` 的集成必须提供匹配的 `acceptance_pause_id`。旧 token、已消费命令或没有 token 的底层命令不能授权另一批验收。派发失败且尚未增加额度时，可以重新明确继续，不会被先前的合并点击永久阻塞。

暂停状态、统计、确定性聊天提示与 SSE 事实均持久化。后台没有自动续跑或无限重试。

## 已有卡死任务的兼容范围

仅支持 GitHub `main` 的已核验基线 `a6c3ca215d72b6335e5301a04616e9b627acf81c`，且该任务必须是旧版 `stalled`、原因恰为 `Final candidate attempt limit reached`，已归档结果也确认为 `candidate_limit_reached` / `not_run`。程序按旧版源码指纹及原件哈希核对，不接受任意其它旧引擎或同名错误。

应用先只读核对原件，显示恢复入口。只有点击继续后，内核再次核验任务身份、预算、原始快照、当前源码、冻结验收、运行环境及未知结果保护，才能提交这一次明确的兼容升级。旧版没有保存批量大小，使用当时已完成的轮次数作为这次及后续批量大小。

旧版在 `stalled` 后可能已清理原 Docker 容器。如果原绑定环境已丢失、被改动、停止没有可信回执，或任何请求/操作结果仍未知，程序保留现场并拒绝续跑；不会自动重建容器、换任务身份或重放副作用。其它旧任务继续使用自己的冻结版本。
