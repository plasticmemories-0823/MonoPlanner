# 按原文证据纠正冻结预期

规则版本：`verbatim-expectations-v2`。适用于新版本启动的任务，不自动把已有任务的检查点迁移到新内核。经用户明确批准的独立评测续接仍须单独审计、冻结和保留原件。

## 使用流程

当充分独立证据说明生成的冻结验收预期有误时，模型可调用 `revise_acceptance`，提交完整新 `test_code`、原文引用及逐项纠正。源码工作区不在此工具中修改。

1. 校验原始快照清单、文件内容和来源身份。
2. 精确匹配引用的原文，不清理空白、不自动纠字、不模糊匹配。
3. 校验所有旧片段在当前**已冻结**的验收中各自唯一、互不重叠，且完整新代码恰好等于这些替换。
4. 校验改动仅发生在可以明确识别的预期字面量中。
5. 保存新提案，在原始源码上试跑，返回真实结果；模型查看后须另行调用 `freeze_acceptance`。
6. 再按新冻结验收验证候选。引用匹配或冻结本身均不代表任务通过。

若正处于修订提案的试跑阶段，再提交纠正仍以当前已冻结版本为基准，完整列出所有修订，不能把尚未冻结的草稿当成新基准。`trial_id` 使用最近的待确认提案 ID；没有待确认提案时使用当前冻结 ID。

## 工具字段

原有 `trial_id`、`reason`、`test_code`、`test_driver` 保留。新增数组字段如下；冻结前修订和普通运行准备修订都传空数组。

```json
{
  "evidence": [
    {
      "id": "required-value",
      "source": "task_request",
      "quote": "return 4"
    }
  ],
  "corrections": [
    {
      "before": "self.assertEqual(value(), 2)",
      "after": "self.assertEqual(value(), 4)",
      "evidence_ids": ["required-value"],
      "reason": "任务原文明确要求返回 4；旧预期 2 与该要求冲突。"
    }
  ]
}
```

`quote` 是相关原文的完整、连续引用。必须来自所声明来源；不能加入省略号、改写或修正排版。每个修订必须引用至少一条证据并说明理由，证据 ID 不重复、不悬空、不闲置。旧字面量重复时，把所属断言等未变上下文一并放入 `before` 和 `after`，而非任意选择第一次匹配。

允许的来源：

| `source` | 程序读取的原件 |
|---|---|
| `task_request` | 当前任务已记录的原始请求 |
| `user_update:<id>` | `user_updates` 中已持久化的明确用户补充，使用原记录 ID |
| `original_file:<path>` | 开工时冻结快照中的 UTF-8 文件，路径必须是清单内的规范相对路径 |

工作区的新文件、修改后的内容、当前实现输出、模型产物和网络页面不提供这条修订通道的解锁依据。已读取的原文可以从历史操作记录复查；原文件后来改变时，核验仍读取保留的开工快照。引文按解码后的 UTF-8 字符串精确匹配，保留 BOM、CRLF 和空白。

来源不存在、引文缺失或不一致时返回：

> 未找到原文或原文错误 请输入完全一致的原文

此时不产生新提案、不改冻结验收、不执行工作区修改；模型可修正提交。非法来源和越界修改给出对应拒绝原因。原始快照或已存证据被篡改属于完整性冲突，停止并保留现场。

## 初版允许的修改边界

- 支持标准 `unittest.TestCase` 测试方法中的 `self.assertEqual`、`assertListEqual`、`assertTupleEqual`、`assertDictEqual`、`assertSetEqual`、`assertCountEqual`、`assertMultiLineEqual`、`assertSequenceEqual`、`assertAlmostEqual` 的两个位置参数；也支持测试函数或方法中的 `assert actual == expected`。
- 支持直接预期字面量，以及只被这些断言作为预期读取的局部字面量变量。局部变量可在测试函数的顺序语句或 `with`／`async with` 主体中赋值，也可在同一块中先断言、再顺序赋值用于下一断言；每次赋值分别绑定到随后的对应断言。支持嵌套 `with`、标量、列表、字典、元组、集合及容器顺序纠正；负数字面量可用。
- 每个赋值必须有对应的预期读取才能修改，被后续赋值覆盖但没有使用的字面量不可修改。只分析同一顺序语句块中的绑定，不猜测跨 `with` 边界、异常抑制、条件分支或循环后的赋值来源。
- 另一侧必须能与预期区分；两边都是常量、同名变量还用作输入、发生别名/修改、非字面量重绑定、其它类型绑定或动态局部变量访问时拒绝。顺序字面量赋值支持不等于允许修改测试输入或控制流。
- 自定义基类或断言、计算表达式、调用生成预期、全局预期变量、断言关键字参数等未支持写法不会自动猜测转换。普通源码修复仍可使用这些写法，只是不能借此修订冻结预期。
- 除预期字面量区域外，其余原文字节保持一致，包括用例、输入、被测调用、断言类型、驱动、消息和注释。`test_driver=[]` 沿用原驱动，不能更换。用户固定验收命令继续不可修改。

程序核验的是来源真实性与修改边界，不证明“充分证据”及理由的语义判断一定成立。模型仍应根据独立要求判断正确预期；没有另加人工批准或审查模型。

## 版本、比较与预算

提案与冻结记录包含规则版本、父版本、原始快照指纹、来源指纹、匹配原文及位置、逐项前后片段与理由、前后代码指纹。记录沿用原有 SHA-256 引用校验，恢复及再次冻结时重新核验。

已经重新冻结的证据纠正会取代它纠正的旧预期。旧版本仍运行并保留对照结果；原先由该预期造成的失败不再独立阻塞最终结果。新版本完整执行所有未修改检查。

普通准备修订可能保留不同的模块准备条件。历史版本与纠正基准具有相同测试行为且旧片段可精确定位时，比较阶段仅将已批准的预期纠正投射到该历史版本，再使用它自己的准备条件执行。这样不会因为预期纠正而丢失其它准备冲突。无法确认旧片段身份时保留原冲突检查，不猜测取代。多次纠正按冻结顺序记录和应用。

修订、试跑和重新冻结不重置验收轮数、时限、模型 Token、费用、请求序号或未知预留。结果不明的试跑仍停止，不自动重放；普通准备修订的冲突检查及冻结前规则保持原样。

## 离线验证和交付

`tests/test_expectation_corrections.py` 覆盖来源、精确匹配和预期编辑边界；`tests/test_expectation_bindings.py` 覆盖 `with`、顺序重绑定和拒绝边界，并用假模型验证重新试跑、冻结、版本比较和断点恢复；`tests/test_evidence_acceptance_flow.py` 覆盖原有证据修订完整流程。测试不调用付费模型。

独立冻结目录记录新源码清单、规则版本和内核指纹。后续评测须标明规则版本变化；不覆盖已经开始题目的旧冻结源码、成绩或账本，也不热切换内核。回滚按本次保存的源码快照及逐项变更清单进行；已有任务仍保留其对应的冻结代码和证据。
