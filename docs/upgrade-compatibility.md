# 升级与旧任务续跑

1.0.0 正式初版使用应用数据版本 2 和工作管道协议版本 2，作为后续升级的兼容基准。数据与协议版本独立于产品版本，不重新编号；保留有版本应用库的迁移，无版本应用库不迁移。
旧任务仍绑定创建时的冻结内核，不自动采用新版提示或验收规则；能否继续执行还取决于协议及失联保护是否受支持。

## 三种身份

| 身份 | 用途 |
|---|---|
| 应用数据版本 `2` | `application.sqlite3` 的 `PRAGMA user_version`；版本 1 迁移前备份，事务增加命令停止身份字段 |
| 工作协议版本 `2` | 宿主和工作进程的私有 JSON 管道；运行、控制、查询与存活心跳 |
| 内核包 ID | 源码、资源、运行时引用与文件哈希清单的摘要，任务只绑定一次 |

应用数据库迁移必须提供连续的迁移步骤，先用 SQLite backup 保存完整备份，再事务更新并检查完整性。
失败恢复原库，保留备份。遇到更高版本或无迁移路径时停止写入，不猜测格式，也不自动清空数据。
工作检查点、原始需求、冻结验收、累计预算和资源原件不属于应用表迁移范围。

## 新版应用与固定内核

开始工作前在状态目录保存 `engines/<ID>` 和 `engine-runtimes/<ID>`。
前者包含工作所需源码、提示、Schema、驱动及必要许可证；旧内核包仍保留其原有运行资源；后者包含固定 Python、生产依赖、Git 和 Node。
同一运行时与内核被多任务共用，不复制前端和个人凭据。删除旧安装目录不会删除这些已绑定资源。

`tasks/<任务ID>/engine-binding.json` 记录协议版本和内核 ID。恢复只解析这一绑定，不能用当前源码替代丢失或损坏的旧内核。
内核校验全部文件清单、内容哈希以及原生源码身份，继续核对原容器、源码、验收和操作配对。
没有完整绑定的旧任务、未知模型结果或不明操作均不会被升级逻辑自动重发。

旧协议 1 的任务保留读取与停止能力；它缺少当前的失联保护，不能在新版里直接重新执行。当前不提供通用自动迁移入口；需要继续时必须针对原记录单独评估并明确迁移，核验原件、环境、累计用量与未知预留，不能把更新应用当作迁移授权。从协议 2 基准开始，未来宿主仍通过受支持的版本协议调用任务绑定内核。

网页与 CLI 经过同一工作桥接。宿主保留一个工作调度位置，内核继续持有原任务租约和唯一原生检查点。
控制消息保留原命令 ID、暂停 ID 和应用结果；普通补充不增加验收额度。
工作消息不混入 Chatbot 上下文。管道断开或心跳超时后停止新派发并尝试终止所属工作；容器自身通过只读续租和看守提供有界超时停止。只有实际停止经核验后才显示成功，不能承诺零延迟。详见[失联保护](lifetime-safety.md)。
控制管道与命令标准输入输出隔离，子命令不能读取宿主控制消息。

凭据只经私有管道交给内核，不在任务参数、内核包或进程命令行保存。
原生任务及资源台账保持自身格式，旧内核不直接读写升级后的应用表。
有任务引用的内核不得回收；绑定损坏时停止回收，不能猜测其引用关系。

## 后续版本的发布要求

每次改动数据或工作接口，都要用基准内核建立真实离线任务，再用新版应用完成暂停后的续跑，核对操作、验收、用量及未知结果保护。
同时验证新任务采用新内核。未来协议新增能力需要显式版本适配；不能重新解释已发布协议的字段含义或把旧任务静默转换为新任务。
升级前应退出应用；升级后仍需明确继续任务，不因安装、刷新或打开界面自动产生模型请求。
原环境或必要内核已被外部删除时只能说明缺失，不能保证从缺少证据的现场恢复。

任务检查点采用连续哈希原件，SQLite 是可核验的索引。应用重启不自动推进任务；用户点击继续才进行断点续接。具体回执核验、未知费用和部分执行规则见[崩溃后的手动断点续跑](crash-continuation.md)。


继续命令、额度追加和停止身份见[人工继续原任务](unified-continuation.md)。继续不清零累计消耗，也不替代权限或迁移授权。
