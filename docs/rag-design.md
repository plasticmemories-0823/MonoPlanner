# MonoPlanner RAG 设计访谈

本文件保留检索流程的设计决定。已取消的动态参数调整方案不再保留；检索参数固定于
源码。实验实现与实际验证状态见 [rag-experiment.md](rag-experiment.md)；下文各次确认中
的“尚未实现”是当时的历史状态。Bench 保持暂停。

## 最新执行规则（2026-10-17）

用户后续确认的“实验版统一搜索与隐式策略清理”替代下文访谈中的默认双路融合、
自动猜符号和向量不可用时自动降级规则：默认完整字面精确搜索，BM25仅排序真实命中；
语义搜索显式选择，向量不可用明确返回。仅语义模式保留请求级一次条件改写，取消融合
权重和双路不一致信号。精确搜索扩展到已授权工作区及资料，语义索引范围仍不扩展。
实际接口、分页与验证限制见 [rag-experiment.md](rag-experiment.md)。下文保留原访谈，
用于追溯决定来源，不能据此恢复已替换的执行器或静默策略。

## 已确认

### Q1：检索资料范围

用户选择 B（2026-10-16）：

- 当前项目源码。
- 项目内文档。
- 当前工作任务的工具结果、编译报错和测试日志。

跨任务历史、其他授权目录和网页资料不属于本次确认的检索范围。
术语定义见 [CONTEXT.md](../CONTEXT.md)。

### Q2：按需改写，主路径不新增模型调用

用户确认 B，并补充以下约束（2026-10-16）：

- 默认由工作 LLM 在现有主流程中产出 query 或工具参数。
- 程序只做确定性补齐：`repo`、`branch`、`commit`、`task_id`、`run_id`、时间范围、排除目录。
- 简单 query 不增加改写费用；主检索路径不新增 LLM 调用。
- 仅在 zero-result、低召回或实体未覆盖时，才允许一次短小的改写调用。

触发判据与预算边界由 Q3 补充。具体检索实现、评分阈值、改写模型及改写失败后的处理仍待讨论。

### Q3：必需证据覆盖、次级软触发与请求级预算

用户确认（2026-10-17）：

- 以必需证据覆盖为主判据；覆盖目标是明确必需的实体及证据类型。
- 保留次级软触发：双路不一致、rerank 无赢家、来源单一、时效错位时，允许一次短改写。
- 单纯命中数量少、探索词未命中不触发。
- 所有触发必须记录原因。
- 每次用户请求最多一次改写预算。同一请求中的多次工具查询与补查共享该额度；多个触发同时出现不增加额度。

软信号的适用边界见 Q4；各信号的具体定义在相应检索、重排和上下文环节继续细化。

### Q4：查询类型决定软信号的适用范围

用户确认（2026-10-17）：

- 软触发必须带适用条件。
- 定位型查询精确命中当前版本即短路，不因单文件来源调用付费改写。
- 诊断／审计型查询才启用时效、多源、双路信号。
- 必需实体已经覆盖，不妨碍适用的软信号触发；不适用的信号必须屏蔽。
- 所有触发和屏蔽都记录日志。

双路执行方式见 Q5；具体索引实现及向量模型尚未决定。

### Q5：诊断／审计默认并行双路召回，必须有成本护栏

用户选择 A，并要求避免成本失控（2026-10-17）：

- 诊断／审计型查询默认并行执行 BM25 与向量召回，再融合、重排。
- 定位型查询继续遵守 Q4 的精确命中短路。
- 成本护栏是实现要求；本次选择不代表允许无界索引、召回或模型调用。

向量化部署位置见 Q6，索引未就绪时的降级见 Q7，重排资源保护见 Q11，共享内存预算见 Q12，单次检索消息预算见 Q13。增量索引范围、召回与重排的具体上限仍需确定。

### Q6：默认使用本地 Embedding

用户选择 A（2026-10-17）：

- 使用本地轻量 Embedding 模型，不使用远端 Embedding API。
- 本地推理的 CPU、内存、并发和批量大小需要受限。
- 具体模型与资源限额尚未选定；上线前需要实际内存验证。

本项只决定向量化部署位置，不改变工作 LLM 的既有调用方式。

### Q7：索引未就绪时显式降级，不阻塞等待完整向量索引

用户选择 B（2026-10-17）：

- 首次或增量向量索引未就绪时，先使用可用的 BM25／精确读取路径。
- 后台在资源限额内建立或更新向量索引，就绪后启用双路。
- 明确标记“向量路未就绪、检索不完整”。
- 屏蔽依赖完整双路的“不一致”信号，并按 Q4 记录屏蔽原因。
- 索引未就绪本身不消耗付费改写额度，也不能据此断言资料不存在。

### Q8：按资料结构优先切分检索片段

用户选择 A（2026-10-17）：

- 代码按函数／类边界切分。
- 文档按标题与段落切分。
- 工具结果按结构化条目切分。
- 日志按操作／事件切分，错误栈保持成组。
- 超长结构继续分片并保留父级引用；无法解析结构时回退到文本窗口。
- 使用解析器与确定性规则切分，不新增 LLM 调用。
- 片段保留原文位置、版本、哈希与父级引用，命中后可以补读完整上下文。

片段长度与重叠上限见 Q9；父级扩展规则见 Q10，总预算见 Q13。

### Q9：较小片段，命中后按需补读

用户选择 A（2026-10-17）：

- 首版目标长度约 256 Token，单片硬上限 512 Token。
- 超长结构拆分时，相邻片段最多重叠 64 Token。
- 能在上限内容纳的完整函数、段落保持完整，不机械切到目标长度。
- 上限计入随片段发送的来源信息，并受最终选定 Embedding 模型的实际输入窗口约束。
- 禁止静默截断；超长内容按 Q8 拆分并保留父级引用。

以上是首版可调整参数，尚未证明最优；具体 Token 计数需与选定模型的分词器及必要特殊 Token 对齐。

### Q10：命中片段返回，上下文显式补读

2026-10-17 按用户要求替换自动父块展开，修复无关父块与返回膨胀：

- 精确搜索返回包含完整字面命中的原文窗口，不推测所属函数或自动附带整个类。
- 语义搜索返回实际检索到的同版本片段，不再自动补读父结构。
- 模型正文只保存在`results`，各命中以`result`索引引用；片段以`source`索引引用共享来源表，路径、版本及哈希不再逐命中重复。完整身份和排序依据保留在本地原件中；同源重叠区间逐字合并，命中坐标不丢失。
- 原件、来源哈希与续查位置保留，需要周边上下文时由模型显式读取；不把片段冒充完整源码。
- 单次预算仍见 Q13；分页按命中数量前进，不按合并后的片段数前进。

### Q11：使用本地 Cross-Encoder 重排

用户选择 A（2026-10-17）：

- 诊断／审计查询对召回后的有限候选使用本地 Cross-Encoder 评分重排。
- 定位型查询精确命中时继续短路，不经过模型重排。
- 限制候选数量、内存和耗时；资源不足或超时降级为规则排序，并记录原因。
- 不调用远端重排 API；本地计算开销必须纳入资源管理。
- 具体模型与限额需要实测，不默认 Embedding、重排模型与 Docker 可以同时常驻。

实现参考：[Sentence Transformers Retrieve & Re-Rank](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)。
该文档说明检索后对查询与候选共同评分的工作方式，不构成本项目效果或资源占用的验证结果。

### Q12：全套本地 RAG 共享 1 GiB 额外内存峰值预算

用户选择 A（2026-10-17）：

- 首版暂定整套 RAG 的额外内存峰值预算为 1 GiB，不是每个组件分别获得 1 GiB。
- 统计范围包括 Embedding、重排模型、加载与推理临时内存及索引缓存。
- 优先给编码任务和 Docker 留空间，通过限制并发、按需加载控制占用。
- 主机余量不足时，即使 RAG 尚未用满预算也要让路，按已确认规则降级。
- 具体模型必须实测选型；超预算则使用更小模型或降级，不自行提高预算。

该预算是首版约束，不代表已经验证所选模型能够装入，也不把模型文件大小当作运行内存占用。

### Q13：单次检索工具消息最多 8,192 个估算输入 Token

用户选择 A（2026-10-17）：

- 首版单次检索工具消息的完整内容上限为 8,192 个估算输入 Token。
- 预算包含原文、来源字段、自动补读、缺失说明和续读位置，不只计算正文。
- 先提供排名靠前的资料；需要时继续补查。
- 放不下的材料保留原件并提供续读位置，不偷偷截断，也不将已返回内容当作全部证据。
- 该数值固定于源码，不提供运行时调整入口。
- 单次检索预算不等于整项任务费用上限，不改变既有上下文压缩规则。

### Q14：允许明确标注的待验证假设

用户选择 A（2026-10-17）：

- 检索资料不足以确定原因时，工作模型可以提出明确标注的待验证假设。
- 区分已有证据、缺失信息、可能原因及下一步核验方式，不能把假设写成已确认结论。
- RAG 只返回证据、缺口和检索不完整标记；假设由现有工作 LLM 在主流程中提出。
- 不新增诊断模型调用，不改变验收标准。
- 检索相关性高不等于结论已被证明。

### Q15：关键事实必须附可核验引用

用户选择 A（2026-10-17）：

- 错误位置、修改依据、实际测试结果等关键事实必须附引用；普通解释和过渡语不逐句引用。
- 程序核对来源、版本／哈希及原文范围。
- 核验通过只代表来源可追溯，不证明该来源支持模型的结论。
- 缺失或失效引用明确标记为未核验，不因此新增付费调用，也不改变执行验收规则。

## 实施与验证

实验版使用固定检索参数；不保留参数候选、决策模型、动态配置数据库或发布流程。
本地 Embedding 和 Cross-Encoder 继续按固定资产清单运行，查询条件由调用方明确提供。

- 验证本地模型的版本、输入窗口、依赖及 Windows 运行方式。
- 模型与索引仍共享原有内存预算，资源不足时按既定规则明确返回不完整状态。
- 保持工具历史、分页、原文哈希、授权过滤、载荷去重及暂停恢复正确。
- 检索分数和引用存在不能代替语义支持或编码验收，不因删去参数调整而放宽规则。
- 检索质量、延迟、成本和内存收益需要实测，不能从离线接线测试推断。

实际功能与验证限制见 [rag-experiment.md](rag-experiment.md)。本轮没有恢复 Bench。
