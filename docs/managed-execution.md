# 受管真实执行验收

生成验收沿用原始源码试跑、明确冻结、候选验收和独立回归。新增 `execution_checks` 声明，由宿主在同一个隔离后端独立执行；不会增加审核模型，也不按题号、题面关键词或函数名称触发。

## 接口

`submit_plan` 首次提交生成验收时必须包含至少一项声明。每项包含：

- `id`：本份声明中的唯一标识。
- `requirement_id`：已确认交付目标 ID；单目标可以省略，不能自行新增或替换目标。
- `requirement_quote`：原始需求或已保存用户补充的逐字片段；空串绑定完整原始要求。引文匹配不证明语义充分。
- `artifact_type`：`generated_code` 表示实际生产入口返回的代码，`repository_entry` 表示交付物本身就是仓库入口；不允许用测试包装脚本替代生成产物。
- `imports`、`setup`、`expression`：绝对导入、输入构造和直接入口调用。程序确认最外层被调用函数来自当前仓库，保存文件哈希；不能把生成输出经过替换或包装后冒充原件。
- `consumer`、`interpreter`：明确编译及运行环境；程序根据固定适配器执行，不接受只调用函数或自行填写成功。
- `python_module`：Python 项目原本使用 `python -m 包名` 时填写模块名，`entry_file` 仍绑定对应的 `.py` 或包内 `__main__.py`。留空保持文件启动。模块的父包须为仓库内带 `__init__.py` 的普通包，命名空间包尚不支持。
- `variables`、`result_variable`、`cases`：数值产物的运行输入及独立预期；不适用的字段为空。

技术适配如下；有独立编译或语法检查入口的语言先检查再运行。Wine CMD 明确记录仅覆盖已执行路径的兼容验证：

| consumer | 程序实际执行 | 仍由原有测试负责 |
|---|---|---|
| `command` | Python 用 `py_compile`、Node 用 `--check`、Shell 用 `-n` 检查原入口；成功后才用对应解释器执行同一文件和字面 `argv` | 业务结果和副作用断言 |
| `command` + Python 模块 | 隔离编译绑定源码，再按已确认的 `python -m 模块名` 与原参数运行，保留包内相对导入语义 | CLI 业务结果和副作用断言 |
| command + wine-cmd | Wine CMD 实际解析并执行未替换的 BAT/CMD 一次，不伪造独立编译回执 | 实际分支、业务和副作用断言；不代表原生 Windows 系统验证 |
| `c_expression` | 将原始表达式放进固定驱动，编译并以指定数值运行 | 额外公开行为及格式要求 |
| `c_statement` | 将原始赋值语句放进固定驱动，编译运行并读取指定结果变量 | 额外公开行为及格式要求 |

库接口和文件交付物通过 `python_tests` 复用同一次标准 unittest 执行，不再给库补一个脚本入口，也不为生成文件指定原要求未指定的脚本名：

- `artifact_type=python_api`：`api_entry` 绑定原仓库的 `模块:函数` 或 `模块:类.方法`，`test_ids` 指定 `test_code` 中的 `类.test_方法`。测试方法实际调用该同步 Python 实现；程序记录来源哈希、编译后的定义与逐测试调用次数。导入、查看函数或替换函数不能充当调用。
- 原要求只指定库范围时，交付目标可用 `模块:*`；`execution_checks.api_entry` 仍必须填写该原模块／包内的具体调用，不能填写通配符或另一个库。
- `artifact_type=file_artifact`：`entry_file` 绑定原交付文件路径。测试中用 `from acceptance_artifacts import read_artifact` 取得 `read_artifact('output/result.json')` 的原始字节，再用正常解析器、加载器和独立断言验证内容。程序核对完整文件、读取前后哈希和测试身份；测试不能自己创建或改写这份交付物来凑通过。

这两种适配目前使用标准 unittest 驱动；不支持替代仓库测试驱动、异步或原生扩展函数的调用见证。单个文件读取上限为 512 MiB，超过时报告能力限制，不截断数据。已有命令、C 生成物和这两类检查可以同时绑定不同的交付目标，仍共用任务的验收时限。调用证据只证明测到了原对象，不能证明断言覆盖了全部业务含义。

数值用例字段为 `values` 和 `expected`，预期必须有独立要求或公开规范依据。宿主对实际数值采用相对容差 `1e-9`、绝对容差 `1e-12`，非有限结果不通过。此版本不提供其它数值精度、其它生成代码语言、任意原生项目构建或浏览器／数据库的专用消费证明；未支持的类型明确报缺口，不自动降级。解释型语言的语法检查并不等于业务验收，运行后仍需原有测试断言。

`call` 和未绑定编译证据的 `executable` 分支已删除，旧声明明确拒绝，不转换成其它模式。每份成功回执必须绑定产物类型、目标运行时及实际运行原件；通常包含编译命令、被编译源码哈希和编译结果，Wine CMD 使用独立的兼容执行范围、Wine 版本原件及执行源码哈希；仓库入口在编译和运行间必须保持同一原件。生成代码则绑定生产入口、未修改的返回文本和固定驱动源码。

声明必须匹配[已确认的原始需求交付约束](confirmed-delivery.md)。工作模型改报另一种产物、语言、入口或输入构造会被拒绝。宿主能证明实际运行和结构化绑定，仍不能仅靠 Schema 证明前厅提取的目标及预期完整覆盖了自然语言需求。

Wine CMD 的环境准备、调用语义和边界见[兼容验收说明](wine-cmd.md)。

## 执行、冻结与恢复

项目导入路径只传入实际执行的工作子进程，不修改宿主环境；Python 编译探针使用隔离模式。确认界面显示模块启动方式与字面参数；宿主核对模块、源码入口和参数，旧记录缺少模块字段时仍按原文件模式理解。

原始试跑与最终验收都使用完整证据的独立工作副本。原始证据始终不可变；副本中允许更新已确认的文件交付路径及已识别的构建缓存。运行输入、Git 跟踪文件和其他未知文件仍受保护，声明输出不能解除这些保护。输出路径由已确认的文件交付目标推导，工作模型不能在验收草稿里自行增加可写路径。文件消费测试还会独立检查读到的交付物在该次测试中未被改写。

文件消费验证工作阶段已经交付的原始字节。与入口执行检查组合时，先核对并保留这份原字节证据，再独立运行入口命令；后续正常重建不会覆盖先前的读取证据。只在验收副本里临时生成文件，不能冒充工作目录已经交付的产物。两阶段共用原来的总时限，已有命令或测试回执阻止直接重跑，必须先调查并接回完整结果。

库接口和文件消费结果与原测试报告、测试源码及对应阶段绑定。已有测试回执但消费结果尚未登记时保留现场，不重跑测试来补证据；完整结果经核验后才能接续。

声明和固定驱动与现有验收文件一起计算身份、保存并检查完整性。既有测试、编译和实际运行共用一个总时限；新增声明没有独立额外时间预算。任何必需声明失败、无回执、超时或无法执行，候选不能通过。源代码或产物的行为失败可以作为原始试跑的缺陷证据；依赖、编译器、导入或配置缺失是不可用，不能当作已复现正确目标。

冻结前可以显式修正声明。冻结后可以通过 `revise_acceptance` 提交有效独立原文证据及完整数组修订，修改模型自拟的声明细节、数值用例与预期；用户确认的产物、语言、真实入口、输入构造及必需输入仍不可更改。`execution_checks=[]` 在没有对应修订时复用当前声明；显式清空必需检查也会被需求校验拒绝。新声明须重新试跑、冻结并产生真实执行回执，详见[原文证据修订](acceptance-evidence.md)。

模型自写测试仍执行，真实执行声明不是删除其它回归检查的理由。明确的用户固定验收命令保持原样，不额外生成声明。只运行补充测试的底层 `AcceptanceRun` API 可以没有声明；模型工作任务的首次验收入口必须提交声明，恢复也拒绝缺少它的生成验收检查点。

同一执行回执已存在时拒绝重放；未知操作按原保护保留现场。源码身份包含新增模块和驱动，旧任务继续要求对应冻结源码，不自动迁移。旧 C 关键词检测、`ARTIFACT_CHECKS` 解析、专属提示模块和旧驱动保持删除，没有双路回退。
